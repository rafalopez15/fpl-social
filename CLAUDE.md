# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this is

FPL is a SwiftUI iOS app for browsing Fantasy Premier League players. It doesn't call FPL directly. It talks to **fplAPI**, a separate FastAPI backend (its own repo) that wraps the FPL API and serves cleaned-up JSON under `/api`. FPL calls players "elements", and the code keeps that name.

Current features: a tab bar (Feed, Players, Notes, Profile), and on the Players tab a player list per position, sorting, search, a stats popover per player, and team short names. Notes lets you write notes tagged with the gameweek (stored on the device, and synced to your account when signed in), and asks why when you make a transfer. Profile links your FPL team by manager ID, and its Account card signs you in with an email code (optional). Feed is a placeholder; the backlog for them lives in Linear (team FPL Social, projects Transfer Notes and FPL Social).

## Build and test

Xcode lives at `/Applications/Xcode.app`, but `xcode-select` points at the Command Line Tools, so prefix commands with `DEVELOPER_DIR`:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer

# Unit tests (fast, no backend needed)
xcodebuild test -project FPL.xcodeproj -scheme FPL \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' \
  -only-testing:FPLTests

# The same under Thread Sanitizer, as CI runs them
TEST_RUNNER_TSAN_OPTIONS=halt_on_error=1 xcodebuild test ... -only-testing:FPLTests -enableThreadSanitizer YES

# UI tests (about a minute, no backend needed)
xcodebuild test ... -only-testing:FPLUITests

# Build only
xcodebuild build -project FPL.xcodeproj -scheme FPL \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro'
```

Use `xcrun simctl list devices available` if that simulator name doesn't exist.

`FPLUITests` covers linking a team, viewing the squad and writing a note. `FixtureServer` (in the UI test target) is a local HTTP server that answers fplAPI routes with the contract fixtures in `FPLTests/Fixtures/` (read from the source tree, which simulator processes can reach), and the tests launch the app with `-FPLAPIBaseURL` pointing at it and `-uiTesting`, which starts with no linked team and no notes and keeps nothing (`LaunchOptions`: in-memory SwiftData and an emptied UserDefaults suite). Both arguments only work in Debug builds. The tab bar's buttons each match three elements (button, icon, label), so tap tabs with `app.buttons["Notes"].firstMatch`; cards combine their texts into one label, so match those with `label CONTAINS`. The tests read what to expect (team name, gameweek, points, captain) from the fixture files rather than hard-coding it, so refreshing the fixtures doesn't break them.

CI (`.github/workflows/swift.yml`, FPL-42) runs on PRs and pushes to `main` that change `FPL/`, `FPLTests/`, `FPL.xcodeproj/`, `Config/`, `.swiftlint.yml`, the workflow or `.github/scripts/`:

- **SwiftLint** on `ubuntu-latest` with the pinned Docker image `ghcr.io/realm/swiftlint:0.65.1`, in `--strict` mode, so warnings fail too. `.github/scripts/summarize_swiftlint.py` reads its JSON report, removes duplicates (the Linux build can report a violation twice), prints the inline PR annotations and fails the job if anything is left. Rules are in `.swiftlint.yml`; `FPLTests/.swiftlint.yml` only raises `file_length`, since most tests live in `FPLTests.swift`. Run it locally with `docker run --rm -v "$PWD":/work -w /work ghcr.io/realm/swiftlint:0.65.1 swiftlint lint --strict`, or `swiftlint lint --strict` after `brew install swiftlint`. Fix violations rather than disabling rules; if a rule doesn't fit the codebase, change `.swiftlint.yml` in its own commit with a reason.
- **Build and test** on `macos-26` with the latest stable Xcode: the unit tests with coverage, under Thread Sanitizer (`-enableThreadSanitizer YES`; the scheme is generated by Xcode and not committed, so it's set on the command line) and `FPL_WARNINGS_AS_ERRORS=YES`, then the UI tests (without coverage, so the comment's coverage is the unit tests'), then a Release build, also with warnings as errors. Both test steps pass `-parallel-testing-enabled NO`: otherwise Xcode clones and cold-boots a simulator per step, which took 3–4 minutes each on GitHub's runners and made the UI tests run several times slower. TSan only logs a race unless `TEST_RUNNER_TSAN_OPTIONS=halt_on_error=1` is set, which makes the test that hit it fail. That aborts the test process, so the result bundle only shows a crash; the step saves xcodebuild's output to `unit-tests.log` and the summary script (`--tsan-log`) adds each race's summary and the top frame of both accesses to the comment. It adds little time, so it runs on every PR. `.github/scripts/summarize_xcresult.py` reads the `.xcresult`: results and failures (Swift Testing included), line coverage of `FPL.app` per file, or the compiler errors if the build failed before tests ran.
- **Warnings as errors:** the project-level `SWIFT_TREAT_WARNINGS_AS_ERRORS` is `$(FPL_WARNINGS_AS_ERRORS)`, and CI passes `FPL_WARNINGS_AS_ERRORS=YES`. Passing `SWIFT_TREAT_WARNINGS_AS_ERRORS=YES` on the command line would also reach the Swift packages, which Xcode builds with `-suppress-warnings`, and the two flags conflict. Locally warnings stay warnings.
- **PR comment:** one comment per PR with the test, coverage, Release and SwiftLint summaries, edited in place on each push (found by its `<!-- ios-ci-report -->` marker), like the API's CI.

Only the build and test job uses macOS, which counts about 10 times Linux minutes on a private repo.

**API contract** (`.github/workflows/contract.yml`, FPL-43): every day at 07:00 UTC, and from the Actions tab, it runs `.github/scripts/fetch_contract_fixtures.sh` against production and then only `ContractTests`, so a backend change the models can't decode fails a check (GitHub emails the failure) instead of reaching users. The same tests run on every PR against the fixtures committed in `FPLTests/Fixtures/`: one real production response per endpoint the app uses, with manager 1 (FPL's own team) for the manager endpoints. The script removes the manager's first and last name (which the API no longer sends, in case they come back) and blanks the region, and keeps the team name. A 503 that outlasts curl's retries (FPL down or updating, as it is for weeks each summer) and the picks 404 before the season's first deadline keep the committed fixture with a warning instead of failing the check; any other error fails. When the backend changes a response on purpose, run the script locally to refresh them and commit them with the app change.

## Backend

- The base URL comes from the `FPL_API_BASE_URL` build setting, per configuration, read through `FPLAPIBaseURL` in `Info.plist` (`FPLAPIClient.configuredBaseURL`, falling back to production). Release always uses the production fplAPI at `https://fpl-api-six.vercel.app/api`, deployed on Vercel with the same responses as local. Both stay on production in the repo. To test against an unmerged backend PR's Vercel preview (`https://fpl-api-git-<branch>-fpl-social.vercel.app/api`, the same URL for every push), pass it on the command line instead of editing the project: `xcodebuild test ... FPL_API_BASE_URL=https://fpl-api-git-<branch>-fpl-social.vercel.app/api`. From Xcode's Run button, add `-FPLAPIBaseURL https://fpl-api-git-<branch>-fpl-social.vercel.app/api` under Edit Scheme > Run > Arguments (Debug only; the scheme isn't committed, so it stays on your Mac) and untick it when done. Don't commit a preview URL; the app PR's "Before merging" section only needs to say to merge the backend PR first. The first request after a few idle minutes can take 1–2 seconds while Vercel starts an instance.
- To work against a local backend, set Debug's `FPL_API_BASE_URL` to `http://127.0.0.1:5000/api` and run it with `uvicorn main:app --reload --port=5000` (its docs say `fastapi dev main.py`, which uses port 8000). `127.0.0.1` only works in the simulator; a physical device needs the Mac's LAN IP and `--host 0.0.0.0`. macOS AirPlay Receiver also listens on port 5000, so with the backend stopped requests get a 403 instead of a connection error.
- `Info.plist` sets `NSAllowsLocalNetworking` so plain HTTP to a local backend is allowed. Production is HTTPS and doesn't need it.

Endpoints the app uses:

| Endpoint | Returns | Notes |
|---|---|---|
| `GET /api/elements/position/{1-4}` | `[Element]` | 404 when empty; the client turns that into `[]` |
| `GET /api/teams` | `[Team]` | Loaded once per launch. `primary_color` and `secondary_color` are `#RRGGBB` or null (FPL-38) |
| `GET /api/fixtures?started=false` | `[Fixture]` | Matches still to be played, by kickoff. Loaded once per launch |
| `GET /api/managers/{id}` | `Manager` | Profile's link flow and linked team. 404 "Manager not found", 503 "FPL is unavailable right now". Called live from FPL, cached up to 60s by Vercel |
| `GET /api/managers/{id}/transfers` | `[Transfer]` | Newest first. `time` has fractional seconds. Checked on launch and on returning to the app for transfer notes; Profile lists them. `is_churn` marks swaps undone while planning a Wildcard or Free Hit; the client drops them. `points_in`, `points_out` and `net_points` (FPL-33) are null until the gameweek is finished |
| `GET /api/managers/{id}/history` | `ManagerHistory` | Points, overall rank, transfers and hit cost per gameweek, and chips used: Notes' gameweek headers and Profile's free transfers. Only those fields are decoded |
| `GET /api/managers/{id}/picks` | `ManagerPicks` | The squad as of the latest deadline: 15 picks with position, multiplier, captain and vice, the chip and automatic subs, and the gameweek's points. Profile's squad. 404 before the first deadline. Only `element` and `position` are guaranteed |
| `GET /api/events/{gw}/live` | `[LiveElement]` | Every player's `total_points` and `minutes` that gameweek (summed in a double), about 670 items. `[]` before the gameweek starts; nulls mean unknown. Profile's squad points |
| `GET /api/events` | `[Event]` | Gameweeks; `is_next` picks where upcoming fixtures start. Loaded with fixtures |
| `DELETE /api/me` | 204, no body | Deletes the account, its synced notes and its teams (Account card). Also 204 when it's already gone; 503 means nothing was deleted. After a 204 the old token is refused |
| `GET /api/me/notes?since=`, `PUT /api/me/notes/{id}` | `NotesPage`, `RemoteNote` | Synced notes (see Notes). Bearer token, 401 like `/me`; 422 for an invalid cursor or note, 404 for someone else's id |
| `GET /api/elements`, `GET /api/elements/{id}` | `[Element]`, `Element` | Wrapped in the client, not used by the UI yet |

The backend returns `503 {"detail": "FPL data is currently unavailable"}` before it has loaded FPL data. Error bodies are `{"detail": "..."}` and the client surfaces `detail` as the error message.

## Accounts

Signing in is optional (FPL-52; design: "Design: accounts and sign-in (FPL-11)" in Linear). Everything that works signed out must keep working without ever showing a sign-in prompt.

- **Supabase Auth** through `supabase-swift`'s `Auth` product only (pinned to an exact version in the project). The project URL and publishable key come from the `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` build settings via Info.plist (`SupabaseAuthService.configured()`). Debug uses **staging**; Release is empty until production has accounts, which makes `AccountStore.state` `.unavailable` and hides the Account card. The publishable key is meant to be public.
- **Testing sign-in:** a staging token only works against a Vercel preview (production rejects it), so run Debug with `-FPLAPIBaseURL https://fpl-api-git-<branch>-fpl-social.vercel.app/api`. Until real email sending (FPL-55), codes only reach `fpl.social.test@gmail.com`, sometimes in spam; other addresses get "Codes can't be sent to this address yet".
- **Test user (Debug only):** with `Config/Secrets.xcconfig` set up (gitignored; copy `Config/Secrets.example.xcconfig` and fill in `TEST_USER_EMAIL` and `TEST_USER_PASSWORD`), the sign-in sheet's email step shows "Sign in as test user", which signs in staging's password test user without a code (`TestUser`, `AccountStore.signIn(as:)`, `AuthService.signIn(email:password:)`), then calls `/me` like the code flow. It shows only in Debug builds, only when both credentials are set, only when the Supabase URL is staging's (`TestUser.stagingHost`) and only when the API isn't production (which rejects staging tokens), so run with `-FPLAPIBaseURL` set to a preview. Its errors show under the button (`SignInModel.testUserError`), not on the email field; a wrong password or an unconfirmed user is `.testUserRejected`. Release builds don't contain any of it: everything is inside `#if DEBUG`, including the error case and the tests that use it. The user exists only in staging's Supabase project (Authentication > Users, auto-confirmed); never create it in production. `Config/Debug.xcconfig` is the app target's Debug base configuration and includes `Secrets.xcconfig` with `#include?`, so builds without it (CI, a fresh clone) just don't show the button. The credentials reach the app through Info.plist's `TestUserEmail` and `TestUserPassword`; don't log them.
- **Flow** (`SignInView`, `SignInModel`): email, then `signInWithOTP` sends a 6-digit code (expires after 10 minutes), then `verifyOTP`, which auto-submits at 6 digits (`.oneTimeCode` autofill). Resend waits 60 seconds, Supabase's limit per address. Supabase gives the same error for a wrong and an expired code. Leave room for the Apple button above the email field (FPL-55).
- **After signing in** the app calls `GET /api/me` once, which creates the account. If it fails (503, or a 401 on a fresh session, meaning the API is misconfigured) the app signs out again and the sheet says "Sign-in is unavailable, try again later".
- **Account requests** go through `AccountStore.withAccessToken`: the SDK's token (refreshed if expiring), a 401 refreshes once and retries, and a second 401 or a failed refresh signs out and the card says "You were signed out". A connection error while refreshing keeps you signed in. `AccountStore.observeSession()` (a `.task` in `ContentView`) also follows the SDK's `authStateChanges` through `AuthService.sessionEnded`, so a session the SDK drops on its own (a revoked refresh token, say) shows as signed out with the same message, without waiting for an account request. Our own sign-out sets the state before telling the SDK, so its event doesn't show the message. `AccountStore.onStateChange` runs as the state changes, before views update; `NoteSync` uses it. The signed-in state carries the user id (`Account.id` from `/me`, or the saved session's at launch), which owns synced notes. `FPLAPIClient.request` adds `Authorization` only to `me` and `me/...` routes, whatever the caller passes.
- **When to ask:** never at launch. A feature that needs an account opens `SignInView(reason:)` from the action itself, with a reason saying what it's for ("Sign in to sync your notes across devices"), and signed-out screens show an inline invitation, never an empty or broken state. Profile's Account card and the Notes tab's invitation row open it; Follow (FPL-54) adds its own.
- **Profile's Account card** (`AccountCard`), right under the team card (or the link form), is the only settings: "Signed in as <email>" and Sign out, which asks first (the user wanted a confirmation here, since signing back in needs a new emailed code). The dialog also says synced notes leave the iPhone until you sign in again, and how many changes would be lost if some haven't synced. Below it, **Delete account** (FPL-51, `AccountStore.deleteAccount`, a destructive button) asks first: "This deletes your account, your synced notes and the teams you follow. Your FPL teams aren't affected." While `DELETE /api/me` runs the state is `.deleting`: not signed in, so sync requests stop (`withAccessToken` needs `.signedIn`), the SDK's events can't say "You were signed out" (`observeSession` only acts on `.signedIn`) and nothing offers sign-in, but the account's notes, waiting changes and cursor stay (`AccountStore.ownerID`, which `NoteSync` keeps notes for). The card shows "Deleting your account…". On 204 it goes to `.signedOut` (the usual sign-out cleanup) before signing out of the SDK, and the card says "Your account was deleted." until the next sign-in. On a failure it goes back to `.signedIn` with nothing to restore, `NoteSync` sends what waited (no upload offer, pulling from the cursor), and the card shows `DeleteAccountError`'s message under the button. A session rejected twice signs out as usual. `withAccessToken` doesn't set "You were signed out" for a request rejected after the state already left `.signedIn`, such as a sync request still running as the account is deleted. This pauses the queue rather than clearing it first (the 7 November architecture decision C), so a failed delete loses nothing; the API refuses a deleted account's writes either way. Email accounts only for now; Sign in with Apple's re-authentication comes with FPL-55. To test it, make a throwaway password user on staging (Authentication > Users, auto-confirmed) and put it in `Secrets.xcconfig`; never delete `fpl.social.test@gmail.com`.
- The session lives in the keychain (`KeychainLocalStorage`). UI tests (`-uiTesting`) run with no auth, so a session in the simulator's keychain doesn't leak in.

Data flow: `PlayersView` owns an `ElementViewModel` (`@StateObject`). `.task(id: viewModel.position)` calls `fetchElements()` on appear and on every position change. The view model fetches players and, until they've loaded, teams and the fixture schedule in parallel. Teams or fixtures failing only hides team names or the popover's fixtures, and they're retried on the next fetch. `filteredElements` applies search and the sort on every read; lists are small (under 300 players per position), so nothing is cached.

## Logging

The app logs with Apple's `Logger` (`Support/Log.swift`), one subsystem (the bundle ID) and a category per area: `network`, `notes`, `linkedTeam` and `account`. Read them in Console.app (filter by subsystem `rafael.lopez.FPL`, and turn on Action > Include Info/Debug Messages) or with `xcrun simctl spawn booted log stream --level debug --predicate 'subsystem == "rafael.lopez.FPL"'`.

- Log at the edges, not in views: `FPLAPIClient.get` logs every failed request, error status and decoding error; `ModelContext.saveNotes(_:)` saves note changes straight away (instead of waiting for autosave) and logs a failed save; `LinkTeamModel` and `LinkedTeamStore` log lookups, linking, unlinking and the transfer prompt. Views call `saveNotes` after inserting or deleting notes.
- Levels: `debug` for detail (each successful request), `info` for notable events (a team found, a note saved, an expected 404, the prompt held back, which repeats on every check), `notice` for things worth keeping (linking, unlinking, a failed lookup), `error` for handled failures (requests, decoding, saves), `fault` for what should never happen.
- Privacy: strings are private by default, but numbers are public, so manager IDs need `privacy: .private`. Mark only safe values `.public`: routes (`FPLAPIClient.route` replaces the manager ID with `{id}`), status codes, counts, server `detail` messages and `error.logSummary` (a decoding error's key path, or the domain and code). Note text, team or manager names and email addresses are never logged. Log the error itself without a privacy option, so it's only readable with a debugger attached.
- Decoding errors log their key path, e.g. "Couldn't decode Array<Element> from GET elements: missing key webName at [3]": most "the screen is empty" bugs will be a mismatch with fplAPI.
- No `print`.

## Model rules

These come from the fplAPI contract. Keep them when touching `Element`:

- Only `id`, `webName`, `team`, `elementType`, `nowCost` and `status` are guaranteed. Every other field is optional because the API sends `null` when FPL changes a field. Don't make new fields non-optional.
- Always decode with `JSONDecoder.fplAPI`. It converts snake_case keys and parses `news_added`, which has fractional seconds that the built-in `.iso8601` strategy rejects.
- Money is in tenths of a million: `nowCost` 62 is £6.2m. Use `element.price` for display.
- `status` decodes unknown codes to `.unknown` instead of failing.
- `team` is the team id (1–20). `teamCode` is a different FPL code; don't use it to look up teams.
- `news` can be `""`. Use `currentNews`, which treats empty as nil.
- `canSelect`, `canTransact` and `removed` (`can_select`, `can_transact`, `removed`) are optional booleans. Use `isSelectable` to decide whether to show a player: it's false only when `canSelect` is false or `removed` is true. Status `u` alone doesn't hide anyone.
- `photo` is a filename only. The API doesn't build image URLs yet.

## Notes

Notes (FPL-10) are personal and stored on the device with SwiftData. `ContentView` builds the container (`Note` and `PendingNoteWrite`, in memory for UI tests) once per launch in `AppModels`, with the `AccountStore` and `NoteSync` that use it, and shares a `GameweekStore` as an environment object. Previews use `NoteSync.preview` and its container, plus `AccountStore(auth: nil)` where notes are listed.

**Sync** (FPL-53, `NoteSync`, `/api/me/notes` from fplAPI FPL-49). Signed out, notes stay on the device exactly as before.

- Every note has a `syncID` (the server's id, the same on every device; filled in at launch for notes saved before syncing), an `accountID` (nil keeps it on this device only) and, for transfer notes, `managerID`. Optional fields so the store migrates.
- Every write site calls `NoteSync`: `added` after inserting (signed in, the note joins the account), `changed` after an edit or undo, `deleting` before `context.delete`. That puts the whole note (or a tombstone) in the outbox, `PendingNoteWrite`, one row per note with its newest version, and flushes. Saving never waits on the network. Undo (`NoteSync.restore`) keeps the sync id and sets `updatedAt` to now, so it's newer than the delete; if the account signed out in the meantime, the note comes back on this device only.
- Flushing PUTs `me/notes/{id}` oldest first and stops at the first failure a retry could fix (offline, 503, signed out); a 404 or 422 drops that change so it can't block the rest. Notes sync on launch, on returning to the app, after signing in and when `NWPathMonitor` says the connection is back.
- Pulling pages through `GET me/notes?since=` while `more`, storing the cursor (and its account) in UserDefaults; a 422 starts over without a cursor. The newer `updatedAt` wins (`NoteSync.apply`): a note from the server replaces this device's copy only if it's newer than it and than any change still waiting, and a deleted one is removed. A PUT's response goes through the same rule, which is how a losing write takes the server's copy. Postgres keeps microseconds and the encoder sends milliseconds, so compare with what was sent, not exact local dates.
- Only the signed-in account's notes are kept: signing out (or the session ending) removes them, their waiting changes and the cursor, and signing back in pulls them again. Device-only notes stay.
- Right after signing in on an iPhone with device-only notes, the sign-in sheet asks "Keep these N notes in your account?" ("Keep in account" / "Only on this iPhone"), once per sign-in, as a step in the sheet rather than an alert (the sheet is still up). It isn't asked at launch with a saved session. Signed in, device-only notes show "On this iPhone only" on their date line. Signed out, the Notes tab's first row is "Sign in to sync your notes across devices", which opens the sign-in sheet; it has no close button and is hidden when sign-in is unavailable.
- The editor and transfer prompt stop at the API's limit of 5,000 (`Note.maxTextLength`, `Note.capped`), counted in code points as the API does, so an emoji can count as several.

- The Notes tab lists every gameweek from the current one (`GameweekStore.current`: `is_current`, or `is_next` before the season) back to 1, newest first. Each gameweek is one card: a list section whose first row is the header (`GameweekHeader`), so swipe to delete, undo and VoiceOver work as in any list. The header shows the title, a green "This week" tag on the current gameweek or a lock on past ones, then "Deadline Sat, Oct 31 · 2 notes" (deadlines from `GameweekStore.events`), and a green `+` (44pt target, labelled "Add note to Gameweek N") that opens the editor for that gameweek. ## Linked FPL team

Profile links your FPL team by manager ID (FPL-30). The link lives on the device; an account isn't tied to an FPL team, and syncing your teams is FPL-54.

**Managers' real names never reach the app** (FPL-45). FPL Social puts anonymous usernames and public comments next to teams, and a real name there makes harassment easy, so the API doesn't send `player_first_name` or `player_last_name` and teams are shown by team name only. Don't add a manager name to any model, screen or saved data. `player_region_name` (a country) is still sent but not shown.

- `LinkedTeamStore` (environment object from `ContentView`) saves a `LinkedTeam` (id and team name) as JSON in UserDefaults under `linkedTeam`, so the link survives relaunches and shows without a network call. `refresh()` fetches points and rank for the card and keeps the saved team name if it fails. Transfer notes (FPL-12) read the manager ID from here.
- The link flow (`LinkTeamModel`): a digits-only field (capped at 10 digits; pasting an FPL URL keeps only its digits), "Find team", then an "Is this your team?" card with team name, points and rank (or the ID for a team with neither yet). Nothing is saved until "Link team". "Not my team" goes back to the field with the ID kept.
- Errors show under the field: 404 "No FPL team with that ID" (red, no retry, since retrying won't help), 503 "FPL is down or updating..." and connection failures (yellow, the button becomes "Try again").
- Linked: a card with team name, ID, overall points, overall rank, last gameweek's points, team value and money in the bank (`last_deadline_value`, `last_deadline_bank`: as of the last deadline, so they don't move until the next one), and free transfers. FPL only gives the signed-in manager their free transfers, so `FreeTransfers.available` works them out from `/managers/{id}/history`: 1 after the gameweek you joined, +1 per gameweek minus those used (never below 0), up to 5, a Wildcard or Free Hit keeps what you had without adding 1 (the user confirmed this against their own team), and transfers already made for the next gameweek are taken off. It can't know one-off top-ups FPL announces mid-season (like 2024/25's AFCON boost to 5); if FPL changes the rules, update it there. A `…` menu in the card's corner holds "Change team" (the current link stays until a new team is confirmed; Cancel returns) and "Unlink team" (confirmation dialog). They used to be buttons below the card; the user moved them up so they don't have to scroll past the transfers.
- Below the card, "Transfers" lists the season's transfers from `/managers/{id}/transfers`, one card per gameweek (latest first, `NamedTransfer.byGameweek`), with the date and, when one was written, the transfer note. The "TRANSFERS" header shows "Net after hits +49 pts" on the right (FPL-33): the real transfers' `net_points` summed, minus every hit (`event_transfers_cost` from the history), hidden until a transfer has points (`Transfer.net(of:history:)`). The user moved it here from the team card, next to the transfers it sums. Next to the date, each transfer shows its net points (`PointsLabel`): "+2 pts" in green, "−5 pts" in red, "0 pts" in grey, or nothing while `net_points` is null. Net points are raw points (no captaincy or bench) of the player in minus the player out while the player in was owned; a Free Hit transfer counts its gameweek only. `FPLAPIClient.transfers` drops churn rows: in chip weeks FPL lists every swap tried while planning (manager 1's Wildcard has 34 rows for 14 transfers). In chip weeks the API also builds rows FPL doesn't have, pairing a real in and out, so notes are matched to transfers on gameweek and both players (`Note.forTransfer`), not time. If the backend's database is down, a chip week comes back with no churn marked; Profile then shows the extra rows, `NamedTransfer.id` includes the time so a repeated swap doesn't clash, and the transfer prompt waits while any gameweek has more than 15 new transfers (`Transfer.hasUnmarkedChurn`), more than a squad has players. Tapping a transfer (rows end in a chevron) opens its note, or starts one in `NoteEditorView(gameweek:transfer:)`: a transfer note filed under that transfer's gameweek and dated by it, the same as one from the prompt, so it shows on Notes and in the popover. Notes for past gameweeks lock once saved, as elsewhere; the user chose this. They load with `refresh()`, together with the player names from `/api/elements`, and update when the transfer prompt finds new ones. This list is from the API and covers the whole season; transfer notes only exist for transfers made after linking.
- Between the card and the transfers, "Your squad" (FPL-36, `SquadView.swift`, `PitchView.swift`) shows the squad from `/managers/{id}/picks`: a card headed "Gameweek 9 · 45 pts" with points on the bench underneath and the chip (e.g. "Triple Captain") on the right, then the starting XI on a pitch and the bench on a navy strip below it (in substitution order, each labelled with its position: GKP, DEF, MID, FWD; the user preferred that to FPL's 1, 2, 3, and VoiceOver still reads "bench 1" etc.). The pitch is drawn with a `Canvas` (`PitchBackground`): a top-down half pitch, goalkeeper at the top and forwards on the halfway line, in muted greens (`Theme.pitch`, `Theme.pitchStripe`) rather than FPL's bright green so it sits in the navy theme; the tilted 3D pitch FPL uses was skipped because it narrows the top rows. Each player card is a flat shirt in the club's colors (FPL-38, `KitShirt`): a drawn silhouette (`ShirtShape`) filled with `primary_color`, with a thin collar in `secondary_color`. The user found SF Symbol shirts with an outline too cartoonish and chose this minimal look over a club-colored disc. White kits (Fulham, Leeds, Spurs) stand out on the green by themselves; only kits under 3:1 contrast against the pitch or the navy bench (Newcastle's black, Everton's navy) get a faint 1pt white hairline (`KitColors.needsHairline`, in `Theme.swift` with the hex tokens it measures against). The shirt's size is a `@ScaledMetric`, so it grows with Dynamic Type like the names until the list takes over at accessibility sizes. The API only has traditional home colors, not exact kits, and no goalkeeper kits, so every goalkeeper wears `Theme.goalkeeperShirt` (pink, #F472B6: no club plays in it, and it can't be confused with the app's green, warning yellow or danger red; the user switched from yellow, which clashed with a doubtful flag). A club with null colors (e.g. newly promoted before the backend knows it) falls back to grey `Theme.shirt`. FPL's kit images weren't used because they're FPL's branded artwork. Then the name on a navy plate (in the flag's yellow or red when flagged), and his points that gameweek (FPL-37) on a plate below. Points come from `/events/{gw}/live` for the gameweek the picks came back with (`entry_history.event`), times the pick's multiplier, so a captain shows double and a triple captain triple; bench players (multiplier 0) show their own points, as FPL does. They add up to the header's points and points on the bench. "–" means yet to play: his team still has a match that gameweek that hasn't kicked off and he has no minutes, since FPL's 0 minutes looks the same before and after a match (`LivePoints.score(for:team:)`); in a double where he's played the first match, his points so far show. If the live call fails the card shows the next opponent on its difficulty color instead ("NFO (A)", "NFO +1" for a double, "–" for a blank), so the squad still shows. `refresh()` reruns when the app becomes active, so points move during a live gameweek; responses are cached up to 60s. Top left: a green C (TC for a Triple Captain) or navy V. Top right: a green up arrow or red down arrow for automatic subs, otherwise the flag's triangle. A 5-man line fits on a 402pt iPhone because the pitch runs into the card's padding and names shrink to 70%. Cards open the Players tab's stats popover without the Season and Advanced stats (`showsStats: false`; the user found it too much here), so it shows the header, news, your latest transfer of the player and fixtures. It opens below the card when it's in the top half of the visible scroll area and above it otherwise (`onGeometryChange` in `.scrollView` space), so it always has room. There's no Pitch/List toggle: the user prefers fewer controls. The user chose the placement above transfers, the popover and the pitch. FPL only publishes picks at the deadline, so a footnote under the latest squad says transfers since then aren't shown yet. A `‹ GW 9 ›` stepper on the right of the "YOUR SQUAD" header (`GameweekStepper`, added at the user's request) goes back through earlier gameweeks, from the one the manager joined (`startedEvent`) to the latest (`LinkedTeamStore.squadGameweeks`); the arrows step one gameweek and the label opens a menu of them all, and VoiceOver can swipe up or down on it. The stepper is hidden until the latest squad loads, and with only one gameweek. `LinkedTeamStore.squad` (`SquadState`) loads with `refresh()`: placeholder rows while loading, "No squad yet" on a 404, "Couldn't load your squad" with Retry on a 503 or other failure; a failed refresh keeps a squad already shown. ## Transfer notes

When you make a transfer in FPL, the app asks why (FPL-12). Decisions are on the ticket.

- `LinkedTeamStore.checkForTransfers()` runs on launch, when a team is linked and when the app becomes active (`ContentView`). It fetches `/managers/{id}/transfers`, keeps those made after `transfersSeenUntil` (UserDefaults), resolves names from `/api/elements` and sets `pendingTransfers`. Linking sets `transfersSeenUntil` to now, so the season's earlier transfers are never prompted. FPL doesn't push transfers and Vercel caches for 60s, so a new transfer can take a minute to show.
- `ContentView` shows `TransferPromptView` while `pendingTransfers` isn't empty: one card per transfer (IN with price, OUT, a "Why did you bring in X?" field) and one Save. Later and Save both save a `Note` per transfer, with `transfer` set (`NoteTransfer`: both players, the price paid for the player in, what the player out sold for (`outCost`, FPL's `element_out_cost`, which can be below his price then because FPL keeps half of any rise), time), `gameweek` = the transfer's `event` and `createdAt` = its time, then `finishPrompt()` moves `transfersSeenUntil` past them. Swipe-to-dismiss is disabled so transfers can't be lost.
- A skipped transfer note has empty text. It shows on the Notes tab as "Why did you bring in X? Tap to write it." and stays editable even in a past gameweek until written once (`Note.isLocked` ignores empty text).
- The stats popover shows your latest transfer of the player this season (`Note.latestTransfer`), from `LinkedTeamStore.transferHistory` so it covers transfers made before linking: "Bought in GW9" with the price paid, or "Sold in GW8" with the selling price and who replaced him, then the transfer's net points ("+2 pts vs Watkins" when bought, "Isak +3 pts vs him" when sold, the user's wording; colored like the rows), then the note from that transfer if there is one ("No note written." for a skipped one). Nothing if he wasn't transferred this season or no team is linked. Before the history has loaded it falls back to transfer notes. `ElementRow` passes the history in. The user wanted this in the popover, not as a tag on the list rows.
- The popover's `@Query` needs `.modelContext(modelContext)` passed from `ElementRow`: popover content didn't inherit the model container and the query came back empty.
- To test the prompt without making real transfers, launch with `-transfersSeenUntil "<date>2026-10-28T00:00:00Z</date>"` (argument-domain UserDefaults) after linking manager 1.

## Loading state

`fetchElements()` numbers each request (`fetchGeneration`) and only the newest one writes state. Its `defer` always clears `isLoading` for the newest request, including on cancellation. Don't go back to checking `Task.isCancelled` and returning early: pull-to-refresh used to swap the list for the full-screen spinner, which cancelled the refresh and left the spinner running forever.

The full-screen spinner shows only when `isLoading && elements.isEmpty`. Refreshing keeps the list on screen with the system spinner. Switching position clears `elements` so the old position's players never show under the new title.

## Design

The app uses the **Floodlights** theme (picked from three directions suggested by the ui-ux-pro-max skill): midnight navy surfaces, one green accent, SF Pro type. It is dark mode only: `UIUserInterfaceStyle` is `Dark` in `Info.plist`, so don't add light-mode variants or `preferredColorScheme` calls.

- **Colors** live in `Theme` (`Theme.swift`): `background` #0F0F23, `surface` #1B1B30 (cards, rows, tab bar, popover), `border` #27273B, `text` #F8FAFC, `secondaryText` #94A3B8, `accent` #22C55E (also `AccentColor` in the asset catalog, so `.tint` and buttons pick it up), `onAccent` for content on green, `warning` #FBBF24 for injury news. All text colors pass 4.5:1. Use `Theme` instead of literal colors.
- **Applying it:** every screen calls `.themedScreen()` (navy background, hides list/form backgrounds) and list or form rows call `.themedRow()`. Sheets set `.presentationBackground(Theme.background)`, popovers `Theme.surface`. The player list uses `.contentMargins(.top, 4, for: .scrollContent)` to remove the grouped style's large top gap. Don't override text with `foregroundStyle(_:_:)` on a container: it turns `ContentUnavailableView` descriptions white. System `.primary`/`.secondary` text is fine on navy.
- **Fonts** stay SF Pro with Dynamic Type text styles. Don't add custom fonts.

- **Navigation title** is inline and doubles as the position menu (`.toolbarTitleMenu`). With a large title, iOS only shows the menu after scrolling.
- **Tab bar** is custom (`FloodlightsTabBar`), not the iOS 26 system one: the user found its glass selection animation too busy. A rounded bar with a solid green pill behind the selected tab. It sits on a soft edge (`SoftEdge`): a blur and navy gradient that start 16pt above the bar (counted in the bar's height, so lists' last rows scroll fully clear of it), so rows fade into navy as they pass under it, matching the scroll edge effect under the search bar. `safeAreaBar` was tried for the system effect but didn't reach the tabs' lists. The bar card is Liquid Glass (`.glassEffect`) on iOS 26 and solid navy with a border on iOS 18; switching is instant with a selection haptic. Tabs live in a `ZStack` (unselected ones hidden with opacity, hit testing and accessibility off) so each keeps its state, and the bar is a `.safeAreaInset(edge: .bottom)` so lists scroll clear of it. It carries `.isTabBar` and `.isSelected` traits for VoiceOver. The bar's `safeAreaInset` doesn't reach lists inside each tab's `NavigationStack` (their safe area reads 0 there), so `ContentView` measures the bar and passes its height as the `tabBarClearance` environment value; `themedScreen()` adds it as a bottom content margin. Any new screen must use `themedScreen()` or its last rows will sit under the bar. Feed, Players, Notes, Profile, each with an SF Symbol and a label; keep it at five tabs or fewer and put secondary screens inside a tab's stack. Unbuilt tabs show a `ContentUnavailableView` describing what will appear there.
- **Search and sort** on the Players tab sit at the top, because the tab bar owns the bottom: `.searchable` with `.navigationBarDrawer(displayMode: .always)`, and two buttons top right. The first is a `Menu` with an inline `Picker` listing the sort fields (checkmark on the current one); the second (`arrow.up.arrow.down`) flips high-to-low and low-to-high. There is no filter sheet.
- **Rows**, left to right: an `info.circle` button, `webName` with the team short name in grey caption text, then price (secondary) and the sort stat (semibold) as fixed-width trailing columns so numbers line up. Rows are one line: news is not shown in the row.
- **Flagged players** (`element.availabilityFlag`) get a colored name and an `exclamationmark.triangle.fill` icon just before it (between the info button and the name), labelled with `availabilityDescription` for VoiceOver. **Yellow** (`Theme.warning`, `.doubtful`): a 1–99% chance of playing next round (FPL uses 25/50/75). **Red** (`Theme.danger` #F87171, `.out`): a 0% chance, which covers injuries with or without a return date and suspensions; news containing "Unknown return date" is always red. With no chance from FPL it falls back to status (`d` yellow; `i`, `s`, `u`, `n` red). The user asked for a "hazard emoji"; the SF Symbol was used instead so it takes the theme color.
- **Players who left the league are hidden** (`element.isSelectable`): hidden when FPL's `can_select` is false or `removed` is true (joined another club, released, not in squad). Missing fields mean the player is shown. Hide them in the app rather than the API, because transfer notes and the feed will still need to show departed players.
- **Right-hand stat follows the sort**: points for points and price, `G` for goals, `A` for assists, a percentage for selected by.
- **Stats popover** uses `.presentationCompactAdaptation(.popover)` so it stays a bubble on iPhone. Sections are 12pt apart with a `Theme.border` hairline between them, and stat labels stay on one line (footnote size). It shows full name, position and team, ownership on its own line, then a news callout (in the flag's yellow or red with the hazard icon when flagged, grey otherwise; falls back to `availabilityDescription` when a flagged player has no news, and shows "Updated 3 days ago" from `newsAdded`), then Fixtures, then Season and Advanced stats in a two-column grid. Missing values show as "–".
- **Fixtures** in the popover cover the next 3 gameweeks (the `is_next` gameweek and the two after it, fewer at the end of the season), one column each: `GW10`, the opponent's short name with (H)/(A), and a 1–5 difficulty chip from the player's side (`team_h_difficulty` at home, `team_a_difficulty` away) colored by `Theme.difficultyColors` (green easy to dark red hard, following FPL). A blank gameweek shows "–" rather than skipping ahead; a double stacks both fixtures. Upcoming means `started == false`, not `finished`, which FPL only sets once bonus points are confirmed. Postponed matches (no `event`) aren't shown. With no schedule (empty list, 503, season over) the section is hidden.
- Changing position keeps the sort field and order.
- The row's info button uses `.buttonStyle(.borderless)` so tapping the row doesn't open the popover.

The user prefers fewer controls: a minimum-stats section, a player count, and then the whole filter sheet with its max price slider were removed on request. Ask before adding controls.

## Pull requests and commits

Shared with the fplAPI repo.

**PR title:** `FPL-<n>: <what the PR does>`, imperative and specific, e.g. `FPL-26: Fixtures endpoint with difficulty ratings`. The issue id links the PR to Linear.

**PR description:**

1. First line: `Closes FPL-<n>.` if the PR finishes the ticket, or `Part of FPL-<n>.` if the ticket has work left (e.g. a backend half). "Closes" makes Linear mark the ticket Done on merge.
2. One or two sentences on what the PR does for the user or app, not how.
3. `## Changes`: short bullets, one per real change, each giving the specific behavior and the reason, and naming the files, fields or screens involved. No bullet should fit an unrelated PR unchanged.
4. `## Testing`: what was checked and how (tests, simulator or device runs, which screens and cases). Say plainly what wasn't checked yet.
5. Extra sections only when needed: `## Breaking change`, `## Before merging`, `## After merging`.

**Style:** plain, direct sentences. No emoji in headings, no bold for emphasis, no em dashes. No filler or hype ("robust", "seamless", "leverage", "streamline", "This PR introduces..."). Concrete facts over adjectives: numbers, field names, endpoint paths, before/after behavior. No closing summary paragraph. No AI attribution anywhere, in PRs or commits: no "Generated with Claude Code", no Co-Authored-By lines.

**Commits:** one logical change per commit, each leaving the app working. Short imperative subject, then a body explaining what changed and why.

**Branches and merging:** start each story on a fresh branch from an up-to-date `main`, named with the issue id (Linear's branch name works). Merge PRs with a merge commit, not squash.

## Conventions

- Deployment target is iOS 18, built with the iOS 26+ SDK. Wrap newer APIs in `if #available(iOS 26, *)` with an iOS 18 fallback.
- Swift 6 language mode, so concurrency checking is complete and data races are errors, and Swift 6 also checks actor isolation at runtime. View models are `@MainActor`; pure helpers on views (like `PointsLabel.text`) are `nonisolated` so tests and models can call them.
- Tests use Swift Testing (`@Test`, `#expect`), not XCTest. Decoding tests build variants of the fixture in `ElementDecodingTests` (the API's example response for Raya); only `ContractTests` reads the JSON files in `FPLTests/Fixtures/`.
- Don't commit `.DS_Store`, `xcuserdata` or the local `// xcode: set sdk=iOS` line in `FPLApp.swift`.
- Keep code comments short: one or two lines saying what the code can't, such as why it's done this way, a non-obvious constraint or what nil means. Don't restate the code, and leave out history (ticket numbers, what was tried, what the user picked); that goes in commits, PRs and this file. The user asked for this after reviewing PR #13.
